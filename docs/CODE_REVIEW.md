# Code Review TurBox — технические выводы

Дата: 21.08.2026

## Общая оценка

TurBox — не набор бесполезных экспериментов, а рабочий прототип с накопившимися историческими слоями. Основная проблема исходного проекта — не алгоритм поиска как таковой, а смешение ответственности и отсутствие надёжной границы между чистой логикой и Selenium.

## Сильные стороны исходного решения

1. Есть реальные end-to-end сценарии, которыми владелец пользуется в работе.
2. Конфиг позволяет быстро собирать десятки поисковых комбинаций без правки Python.
3. `searchMinPriceData` реализует полезную бизнес-логику: ищется не только заданная дата, но более выгодный вариант рядом.
4. Есть hotel-mode, который сравнивает один отель из разных городов вылета.
5. `sub_id` уже несёт маркетинговые признаки и может стать основой аналитики воронки.
6. `browser.py` уже начал выполнять роль общей точки создания ChromeDriver.
7. При ошибках сохраняются debug screenshots / HTML snippets, причём код уже учитывает риск утечки cookies.
8. Реальный успешный output от 19.08.2026 доказывает, что pipeline не теоретический.

## Главные технические проблемы до Stage 1

### 1. God-file `collection_url_generator.py`

До Stage 1: 1227 строк.

В одном файле находились:
- parsing config;
- собственный DSL;
- URL filters;
- Selenium OnlineTours;
- поиск дат;
- извлечение цены;
- output;
- hotel-mode;
- CLI.

Результат: изменение одного сайта требует снова понимать почти весь файл.

Stage 1 вынес чистые части, но Selenium-блок всё ещё большой. Это основной кандидат Stage 2.

### 2. Слишком много временных ожиданий

Исходный `collection_url_generator.py` содержит **37 вызовов `time.sleep()`**.

Сам по себе `sleep` не является ошибкой, но большое количество фиксированных пауз делает поведение зависимым от скорости сети и JS-рендера.

Целевое правило Stage 2:

> ждать состояние страницы, а не заранее угаданное количество секунд.

То есть использовать `WebDriverWait` на появление/изменение конкретного элемента там, где это возможно.

### 3. Широкая обработка исключений

В исходном `collection_url_generator.py`:
- около 15 `except:` без типа;
- около 23 `except Exception`.

Из-за этого могут смешиваться разные состояния:
- предложений действительно нет;
- элемент ещё не загрузился;
- selector устарел;
- popup перекрыл кнопку;
- произошла реальная программная ошибка.

Stage 2 должен ввести явные статусы и точечные Selenium exceptions в критичных местах.

### 4. TXT одновременно был UI и API

Генератор писал человекочитаемую строку, а следующий Python-скрипт снова разбирал её regex.

Это означает скрытую связанность:

```text
Python -> текст для человека -> regex -> Python
```

Stage 1 вынес parsing в тестируемый модуль, но формат не менял. На Stage 2 правильнее ввести структурированный внутренний результат (`TourOffer`) и JSON, сохранив TXT только как presentation/output.

### 5. Несогласованность `NO_RESULTS`

Генератор способен записать:

```text
89. Пермь, Кисловодск, ...
NO_RESULTS
```

а старый converter ожидал строку с `(Новая дата ...)` и пытался разобрать `NO_RESULTS` как следующую description-line.

Финальный результат при этом фактически просто пропускался, поэтому основная работа продолжалась, но лог был шумным и parser state выглядел ошибочным.

Stage 1 исправляет это без изменения бизнес-результата: известный двухстрочный `NO_RESULTS` пропускается целиком.

### 6. `sub_id` хранит ценную аналитику, но формат даты несовершенен

При строке:

```text
5 - 13 авг
```

первая дата не содержит месяц. Legacy-функция не может полностью восстановить `5 августа` и строит неполное представление.

Нельзя незаметно изменить это на Stage 1: изменение `sub_id` разорвёт сопоставимость старой и новой статистики.

Нужно отдельно утвердить новый schema/version `sub_id`.

### 7. Travelpayouts через браузер — дорогое место

Текущий adapter открывает UI Travelpayouts, управляет login/cookies и генерирует ссылки через DOM.

Пока это рабочая реализация и Stage 1 её сохраняет.

После live-подтверждения стоит проверить официальный API партнёрских ссылок именно для OnlineTours. Если API подходит, `link_converter.py` должен стать одним из adapters, а не единственным способом конвертации.

### 8. Старый TopHotels дублирует более зрелый HotelIQ

`top_hotels_parser.py` из старого pipeline не используется четырьмя актуальными BAT.

Его дальнейший рефакторинг внутри TurBox создаст второй независимый код TopHotels. Правильнее подключать HotelIQ как отдельное ядро/сервис после стабилизации обоих проектов.

### 9. Git не отражал реальную рабочую версию

В исходном архиве четыре актуальных BAT были untracked, а множество старых файлов tracked/modified.

Это делало Git ненадёжной точкой восстановления.

Stage 1 создаёт clean baseline repository.

### 10. Credentials уже были tracked в старой истории

`.gitignore` не удаляет уже tracked-файл из Git. Поэтому наличие `travelpayoutsSetup.txt` одновременно в ignore и старом index не защищало прошлые commits.

Stage 1 сбрасывает историю в новой копии проекта и не добавляет credentials/cookies в новый commit.

## Метрики основных файлов

До Stage 1:

```text
collection_url_generator.py   1227 lines | 37 sleep | 15 bare except | 23 except Exception
collection_link_converter.py   477 lines |  2 sleep |  0 bare except |  4 except Exception
link_converter.py              456 lines | 11 sleep |  0 bare except |  8 except Exception
browser.py                     103 lines
```

После Stage 1 структурно:

```text
collection_url_generator.py    ~966 lines
collection_link_converter.py   ~259 lines
+ turbox/* — чистые тестируемые модули
```

Количество Selenium sleeps/except специально почти не менялось: без live browser regression это было бы рискованно.

## Рекомендуемый технический порядок Stage 2

1. Подтвердить live smoke на Windows.
2. Исправить только реально проявившиеся проблемы selectors/waits.
3. Разделить OnlineTours collection и hotel-mode Selenium на два модуля с общим client/browser layer.
4. Ввести внутренние dataclasses/Pydantic-модели.
5. JSON transport между стадиями, TXT оставить для человека.
6. Единый result/error status вместо `None`, `NO_RESULTS` и swallowed exceptions.
7. Проверить Travelpayouts API adapter.
8. После этого объединить два ручных запуска в один orchestration command/BAT.
9. Интегрировать HotelIQ.
10. Затем вводить DealScore и маркетинговую аналитику, потому что к этому моменту data flow будет стабилен.

## Продуктовая рекомендация

Не превращать TurBox в агрегатор максимального количества дешёвых ссылок. Сильная позиция — «радар действительно сильных офферов».

Для этого в будущем нужны три независимых измерения:

1. **экономика:** насколько цена необычна относительно сравнимых вариантов;
2. **качество:** HotelIQ/отель/питание/рейтинг/достоверность данных;
3. **поведение аудитории:** CTR/бронь по `sub_id`.

Именно их комбинация должна стать `DealScore`, а не просто минимальная цена.
